# 《飞花棋》P0「选择产生回声」实施交付文档

> 实施范围：仅实现奇遇选择后的即时、对应、可回看的文本回声。  
> 实施基线：`feihuaqi-playable/` 实际可玩构建。  
> 完成日期：2026-08-16。

---

## 一、任务概述

### 1.1 目标

玩家在奇遇界面点击任意选项后，系统必须立即给出与该选项直接对应的回声，使“选择已被接收、选择导致了什么”一目了然。

本次将交互链路统一为：

```text
点击选项
  → 锁定被选中的 choice
  → 即时展示「已选择：选项原文」
  → 展示该选项专属 resultText
  → 写入本局日志，供回看
  → 结算该选项的属性 / 灵感 / 文心等奖励
```

### 1.2 完成范围

- 覆盖 `config/events.json` 中全部 **14 个 choice 奇遇**；
- 覆盖全部 **28 个选项**，每项都有独立 `resultText`；
- 覆盖两条真实入口：
  1. 棋盘普通奇遇格；
  2. 辞宗战后轻奇遇；
- 兼容旧工程配置：缺少 `resultText` 时，仍返回与所选内容直接关联的确认句；
- 回声同步进入本局日志，短时提示消失后仍可查阅；
- 同步生成 `feihua-content.json`，防止云端工程配置覆盖本地新文案；
- 更新入口版本号，避免浏览器缓存旧 JS / CSS。

### 1.3 明确不在本次范围内

本次没有修改 NPC 台词、主线过场、题库文案、数值平衡、其他 P1/P2 文案任务，也没有部署线上版本。

## 二、实现步骤

### 步骤 1：梳理选择事件与反馈链路

确认当前配置与代码状态：

- 奇遇总数：42；
- choice 奇遇：14；
- choice 选项：28；
- 原配置中 `resultText`：0；
- 原有反馈只有属性 / 灵感浮字、道具 toast 等数值反馈，没有“所选内容产生了什么结果”的叙事反馈。

确认两条选择入口最终都在 `game.js` 读取选项并调用 `applyEffect()`：

```text
普通奇遇：doEvent()
辞宗轻奇遇：runCizongLightEvent()
```

### 步骤 2：建立统一选择处理函数

在 `js/engine/game.js` 新增：

```js
async applyEventChoice(ev, choiceIdx)
```

统一完成：

1. 根据索引取得被选中的 choice；
2. 读取 `choice.text` 与 `choice.resultText`；
3. 生成结构化 echo；
4. 立即调用表现层显示回声；
5. 把事件名、选项、结果写入本局日志；
6. 应用该选项的 effect；
7. 返回 echo，便于测试和后续扩展。

普通奇遇和辞宗轻奇遇都改为调用同一个函数，避免两条入口出现反馈差异。

### 步骤 3：实现专属回声界面

在 `js/ui/hud.js` 新增：

```js
choiceEcho({ choiceText, resultText })
```

显示内容分为两层：

```text
已选择：还他五色笔，从此老实读书
五色光从指间退去。你重新铺纸，第一笔写得很慢，却没有借谁的声名。
```

界面规则：

- 第一行固定为“已选择：+ 选项原文”，直接确认系统接收的内容；
- 第二行为对应 `resultText`，只描述该选择导致的结果；
- 使用独立 `choice-echo` 样式，与普通数值 toast 区分；
- 宽度适配桌面与移动端；
- 展示约 4.25 秒，长于普通奖励提示，保证两行内容可读；
- 使用 `textContent` 写入 DOM，不解析配置中的 HTML；
- 仍沿用 `personalize()`，玩家已起名时，回声中的“你”会替换成玩家名。

### 步骤 4：补齐全部专属回声文案

在 `config/events.json` 的每个 choice 中新增：

```json
{
  "text": "选项内容",
  "resultText": "与该选项直接对应的结果回声",
  "effect": {}
}
```

文案标准：

- 回声必须承接所选动作，不能泛泛表示“选择成功”；
- 两个选项的结果必须能从文字上被区分；
- 不重复报告数值奖励，数值仍由原浮字系统负责；
- 每条控制在 1—2 句，优先写动作、现场变化与直接后果；
- 不引入新的分支状态和数值规则。

### 步骤 5：增加旧数据兜底

若导入旧工程文件、第三方内容或未补齐 `resultText` 的新事件，系统不会静默，自动回退为：

```text
已选择：保留旧选项
选择已确认：「保留旧选项」
```

因此“任何 choice 选择都能收到与选项直接关联的反馈”成立。

### 步骤 6：同步内容包与缓存版本

- 重新生成根目录 `feihua-content.json`；
- 确认其中同步包含 28 个 `resultText`；
- `index.html` 的 CSS 与入口脚本版本号更新为：

```text
?v=20260816choiceecho
```

避免浏览器继续使用旧版 `app.js` 与 `ui.css`。

## 三、关键逻辑说明

### 3.1 为什么在引擎层统一确认选择

没有把回声直接写进按钮点击回调，而是在引擎拿到选择索引后统一处理，原因是：

- 按钮层只负责返回索引，不负责业务结算；
- 引擎层能保证回声与实际应用的 effect 来自同一个 choice；
- 普通奇遇与辞宗轻奇遇可共用同一逻辑；
- 避免出现“界面显示选了 A，实际结算 B”的错配。

### 3.2 回声时序

回声在确认 choice 后立即显示，再执行 effect：

```js
showChoiceEcho(echo);
push(logText);
await applyEffect(choice.effect);
```

这样即使某个奖励会继续打开文心获得 / 替换弹窗，玩家也会先看到自己刚才选择了什么，不会等后续流程结束才收到反馈。

### 3.3 回声与奖励反馈分工

| 信息类型 | 负责回答 | 显示方式 |
|---|---|---|
| 选择确认 | 我刚才点了什么？ | `已选择：选项原文` |
| 叙事回声 | 这个动作导致了什么？ | `resultText` |
| 数值结算 | 属性 / 灵感变化多少？ | 原有浮字 / 奖励提示 |
| 持久回看 | 我之前作出了什么选择？ | 本局日志 |

这种拆分避免把叙事、数值和确认文本挤成一条难读的消息。

### 3.4 对应关系保证

`applyEventChoice()` 只从同一个 `choiceIdx` 取得：

```js
choice.text
choice.resultText
choice.effect
```

三者作为一个整体处理。测试已验证选择第 2 项时：

- 显示第 2 项选项文本；
- 显示第 2 项 `resultText`；
- 只结算第 2 项 effect；
- 第 1 项 effect 不会串入。

### 3.5 日志格式

本局日志记录：

```text
选择「事件名」：选项原文｜结果回声
```

例如：

```text
选择「江郎才尽」：还他五色笔，从此老实读书｜五色光从指间退去。你重新铺纸，第一笔写得很慢，却没有借谁的声名。
```

## 四、最终成果展示

### 4.1 示例一：E006「江郎才尽」

**选择 A**

```text
已选择：还他五色笔，从此老实读书
五色光从指间退去。你重新铺纸，第一笔写得很慢，却没有借谁的声名。
```

**选择 B**

```text
已选择：强留彩笔，搜尽枯肠再赋一篇
你攥紧那支笔，连夜搜尽枯肠。天亮时文章成了，墨色却像从骨头里榨出来的。
```

两条回声分别承接“归还”与“强留”，不会只显示同一种成功提示。

### 4.2 示例二：E012「焚膏继晷」

**选择 A**

```text
已选择：添油再读，直到天明
灯芯爆了一声。你把最后一页读完，窗纸也恰好泛白。
```

**选择 B**

```text
已选择：熄灯就寝，明日再来
你合上书，在页脚夹了一片枯叶，记下明日要从哪一句重新开始。
```

第二项即使 effect 为空，也有明确结果，不再给玩家“按钮是否生效”的疑问。

### 4.3 示例三：旧配置兜底

输入配置：

```json
{
  "text": "保留旧选项",
  "effect": {}
}
```

输出：

```text
已选择：保留旧选项
选择已确认：「保留旧选项」
```
