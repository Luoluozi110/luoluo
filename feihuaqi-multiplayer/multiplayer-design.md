# 飞花棋（回合制大富翁）多人交互方案

> 目标平台：网页端（纯浏览器 ES 模块，已有 `feihuaqi-playable/` 为参考基线）
> 预期规模：同时在线人数少（休闲对局，单房间 2–6 人，单服可承载数千房间）
> 设计基调：服务器权威（Server-Authoritative）的客户端-服务器架构 + 离散回合状态同步

---

## 0. 关键决策（先讲结论）

| 决策点 | 选择 | 理由 |
| --- | --- | --- |
| 网络拓扑 | **客户端-服务器**（服务器权威） | 单点真相、天然防作弊、回合制无需 P2P 的低延迟优势；P2P 无裁判、易作弊、需 WebRTC 信令，性价比低 |
| 传输协议 | **WebSocket**（主）+ WebRTC 数据通道（可选） | 浏览器全支持、全双工、可靠有序，完美契合"离散回合事件"；WebRTC 仅在你追求极致开销时考虑，需额外信令服 |
| 同步模型 | **权威状态快照 + 事件增量**（ON_CHANGE 等效） | 仅在状态变化时广播，绝不逐帧；快照小（数 KB），天然幂等，利于重连 |
| 随机性 | **仅在服务器计算**（骰子/抽牌/洗牌） | 客户端永不掷骰，杜绝结果作弊 |
| 一致性 | **单线程命令队列 + 单调递增 serverSeq** | Node 单线程天然串行化房间状态；sequence 保证所有客户端收敛到同一状态 |
| 会话 | **签名 token + 宽限重连** | 断线不丢状态（服务器持有），重连带 token 即恢复，无需重新加入 |

> 适配说明：当前会话专家为 **GodotMultiplayerEngineer**。本游戏实际是 vanilla JS 网页项目，因此下方以"网页原生"给出可直接落地的参考实现；第 8 节补充了**同一套架构如何映射到 Godot Web 导出**（WebRTCMultiplayerPeer / MultiplayerSynchronizer / 权威 RPC），供你用 Godot 重写客户端时对齐心智模型。

## 1. 网络连接架构

### 1.1 拓扑：客户端-服务器（服务器权威）
- 所有"影响游戏结果"的状态只由服务器写入。客户端发来的消息一律视为**请求（intent）**，经服务器校验后才生效——等价于 Godot 中 `is_multiplayer_authority()` 守卫。
- 拒绝 P2P：棋盘游戏无中央裁判则骰子/交易可伪造；且浏览器 P2P 需 STUN/TURN 信令，复杂度高、收益低。

### 1.2 传输层
- **WebSocket（首选）**：全双工、可靠、有序。回合制每次操作就是一条 JSON 消息，往返延迟同区域约 20–50ms，体验足够。
- **WebRTC 数据通道（可选）**：若追求更低开销/更低延迟，可用 `WebRTCMultiplayerPeer` + 一个极简 WebSocket 信令服交换 SDP；但需处理 NAT 穿透，休闲游戏非必需。
- **心跳**：客户端每 5–10s 发 `ping`，服务器记录最后活跃时间；超时（如 20s 无心跳）判定为连接异常，进入断线宽限（见第 4 节）。

### 1.3 连接分层与伸缩
- **无状态连接层 + 有状态房间层**：连接网关只做鉴权/路由；房间状态集中在"游戏节点"内存中。
- **房间分片（Room Sharding）**：每个房间是独立 `Room` 对象（内存占用仅数 KB）。单 Node 进程即可容纳数千房间。
- **水平扩展**：前置负载均衡/网关按 `roomId` 做**粘性路由**到对应游戏节点；节点间无需共享内存。低并发期甚至单进程即可。
- **持久化（生产可选）**：房间状态周期性快照到 Redis/DB，服务器重启可恢复对局（休闲场景可省略，重启即散局）。

## 2. 实时状态同步机制

### 2.1 同步模型：快照 + 增量
- 服务器持有**唯一权威 `GameState`**。每次提交一个动作后：
  - 推进状态机；
  - 广播**事件增量** `event{serverSeq, type, by, payload}`（其他客户端直接应用，做动画）；
  - 关键节点（开局、重连、重大变更）广播**完整快照** `room_state`。
- 对棋盘游戏而言，完整快照很小（玩家数 × 少量字段），每回合发全量也毫无压力，且**幂等、易重连**。

### 2.2 同步内容分类
| 类型 | 触发 | 模式 | 可靠性 |
| --- | --- | --- | --- |
| 位置（棋子所在格 `tile`） | 掷骰移动后 | ON_CHANGE（仅变化时） | reliable |
| 动作（买地/建房/抽牌/交易/结束回合） | 提交动作后 | 事件增量 | reliable |
| 聊天 | 发送时 | 独立可靠通道，广播给房间 | reliable |
| 回合指针/阶段/计时 | 状态切换时 | 随快照/事件 | reliable |
| 动画/特效 | 收到事件后本地播放 | 客户端本地 | —（无需同步） |

### 2.3 低延迟要点
- **只在状态变化时同步**（绝不一帧一次）——这是回合制最大的带宽/延迟红利。
- **客户端乐观表现**：自己操作后立刻本地播动画，待服务器权威结果到达再校正（棋盘游戏无需回滚，最多"以服务器结果为准"）。
- **操作锁**：未收到服务器确认前，禁止同一步再次操作，避免重复提交。
- **本地预览**：骰子动画可在客户端先滚，但落点以服务器下发的 `dice` 为准。

### 2.4 与 Godot 的对应
- `MultiplayerSynchronizer` 的 `REPLICATION_MODE_ON_CHANGE` ↔ 本方案的**按回合广播**；`syncSchema` 即"哪些 `GameState` 字段对外可见"。
- `MultiplayerSpawner` ↔ 本方案的 **实体生成走服务器指令**（如 `event{type:'spawn_piece'}`），客户端据指令本地实例化，而非手动 `add_child` 跨端不同步。

## 3. 房间 / 匹配系统

### 3.1 房间生命周期
`创建(waiting) → 等待加入 → 开局(playing) → 结束(finished) → （可重赛）→ 关闭`

### 3.2 大厅与列表
- 房间列表接口返回 `{roomId, name, playerCount, maxPlayers, phase, hasPassword}`。
- 创建房间可带选项：`maxPlayers`、`password`、`variant`（棋规变体）。

### 3.3 匹配策略（按规模分级）
- **低并发（当前）**：`quick_match` = 取第一个"等待中且未满且无密码"的房间加入；没有则自动建新房。简单、零等待。
- **进阶（可选）**：基于积分/等级的队列，集齐 N 人后分配房间（参考 Nakama 的 ticket 匹配：提交 ticket → 轮询/订阅匹配结果 → 连接指定房间）。
- **观战**：允许以非参与者身份加入房间（只读），便于测试与直播。

### 3.4 实现要点
- `RoomManager` 持有 `Map<roomId, Room>`。
- 加入校验：容量、密码、房间阶段（仅 `waiting` 可加入）。
- 开局触发：房主调用 `start`，服务器初始化棋子/资金/牌堆，广播完整快照。

## 4. 玩家会话管理与断线重连

### 4.1 会话身份
- 连接/鉴权后服务器签发**签名 token**（HMAC 或 JWT），绑定 `playerId + roomId`。
- 客户端存 `localStorage`，重连时带上 → 服务器据此找回身份与房间。

### 4.2 断线检测与宽限
- 套接字关闭 → 标记玩家 `connected=false`，**启动宽限计时器**（如 45s）。
- 宽限内：房间继续，但该玩家若在"当前回合"，计时结束后服务器**自动跳过其回合**（`turn` 事件 + `reason:'timeout_skip'`），避免对局卡死。
- 宽限内重连：取消计时器，恢复正常。

### 4.3 重连恢复（零状态丢失）
- 客户端带 token 重连 → 服务器定位房间、把新套接字绑回 `playerId` → 下发**完整 `room_state` 快照 + 错过的事件日志** → 客户端重放并续上。
- 因状态全在服务器，**重连不会丢任何进度**。

### 4.4 边界情况
- **同会话双连**：收到带有效 token 的新连接时，关闭该 token 的旧套接字（单会话）。
- **房主掉线**：转移房主给下一位在线玩家（`host = 新 token`），对局不中断。
- **全员掉线**：房间空 → 直接销毁，释放内存。

## 5. 并发数据一致性保障

### 5.1 单线程命令串行化
- 每个房间的状态变更只在**服务器单线程事件循环**内顺序执行，天然无竞态。
- 所有动作进入"当前房间"的顺序处理；每个动作先校验 `room.currentPlayer.token === 请求者`，非当前回合一律拒绝。

### 5.2 单调序列号（收敛保证）
- 服务器对房间维护 `serverSeq`（单调递增）；每条提交事件带 `serverSeq`。
- 客户端按 `serverSeq` 顺序应用；乱序/重复包直接丢弃 → **所有客户端最终状态一致**。

### 5.3 幂等性
- 每条动作带 `clientSeq`；`player.lastSeq >= clientSeq` 视为重复，忽略。防止网络重传导致重复买地/重复掷骰。

### 5.4 服务器唯一定序随机
- 骰子/抽牌只在服务器用 `Math.random()`（或带种子 RNG）计算，结果随事件下发。**不存在客户端模拟**，故无需 lockstep/确定性回放。

### 5.5 原子事务
- 交易（trade）等为两方原子操作：双方均 `accept` 且资源校验通过后才一次性提交；任一方拒绝则整体不生效。
- **只广播完整一致快照或单条原子增量**，客户端永远看不到中间不一致态。

### 5.6 事件日志（可选但推荐）
- 房间维护追加式 `log[]`（动作 + 结果），用于重连补发与复盘/反作弊取证。

## 6. 防作弊基础策略

### 6.1 服务器权威（根本）
- 所有"影响结果"的随机与状态仅在服务器产生（骰子、抽牌、洗牌、资金变动）。客户端只能发**意图**。

### 6.2 服务器端输入校验（每条动作必做）
- 是否该玩家回合？（`currentPlayer.token === 请求者`）
- 参数是否合法？（买地：必须站在可购买格且资金足够；建房：拥有该地产…）
- 实体/目标是否存在？（交易目标 `playerId` 有效）
- 不满足则 `error{code}` 拒绝。等价于 Godot 中 `@rpc("any_peer")` 必须校验发送者与合理性。

### 6.3 不信任任何客户端状态
- 客户端**绝不**上报"我有 ¥5000""我掷出 12"。只上报"请求掷骰"，结果由服务器下发。
- 非权威客户端发来的状态变更 RPC 一律忽略（观战者不能行动）。

### 6.4 频率限制 / 回合锁
- 非自己回合的操作直接拒；同一回合重复操作受 `clientSeq` 幂等保护；聊天限长（≤200 字）+ 限速。

### 6.5 会话安全
- token 签名，不可伪造他人身份；加入房间需 token + 容量/密码校验。

### 6.6 聊天净化
- 转义 HTML、限长、限速；防止借聊天通道注入指令。

### 6.7 异常观测
- 记录异常信号（客户端声称不可能状态、序列号断层）→ 标记/封禁。休闲游戏以"服务器拒绝 + 日志"即可，无需 EAC 级方案。

## 7. 可扩展性与低延迟设计小结

- **扩展**：无状态连接层 + 房间分片 + 粘性路由；单进程数千房间，按需加节点。
- **低延迟**：离散事件同步（非逐帧）、按回合广播、客户端乐观表现、操作锁防重。
- **韧性**：服务器权威 → 重连零丢失；宽限 + 自动跳过 → 对局不卡死；房主转移 → 单点不掉。
- **一致**：单线程串行 + `serverSeq` 收敛 + `clientSeq` 幂等 + 原子事务。

## 8. 与 Godot Web 导出路径的映射（专家视角）

若你用 Godot 4 重写客户端并 Web 导出，本架构可直接平移：

| 本方案（网页原生） | Godot 4 对应 |
| --- | --- |
| WebSocket 长连接 | `WebRTCMultiplayerPeer`（Web 导出）+ 极简 WS 信令服；或桌面/WebView 壳用 `ENetMultiplayerPeer` |
| `token` 会话 | 连接信令后 `multiplayer.multiplayer_peer = peer` |
| 服务器权威状态机 | 服务器节点 `set_multiplayer_authority(1)`，所有状态变更在 `@rpc("any_peer")` 内由服务器校验 |
| `room_state` 快照 | `MultiplayerSynchronizer`（`REPLICATION_MODE_ON_CHANGE`），仅同步对外可见字段 |
| 实体生成（棋子/卡牌） | `MultiplayerSpawner`（场景注册到 `spawn_path`，服务器 `add_child` 自动复制） |
| `event{serverSeq}` 增量 | `@rpc("authority","reliable")` 下发权威事件，客户端按序应用 |
| 防作弊校验 | `@rpc("any_peer")` 内 `multiplayer.get_remote_sender_id()` + 参数合理性校验 |
| 断线重连 | `peer_disconnected` → 宽限计时；重连后服务器重新下发快照 |

核心纪律不变：**客户端只发意图，服务器是唯一裁判**。

## 9. 接入现有 `feihuaqi-playable/` 的落地步骤

1. **抽出纯状态层**：把当前游戏逻辑里的"棋盘状态 + 动作函数"从 UI 中解耦为 `GameState` 与 `applyAction(state, action)`，确保可在服务器运行（无 DOM 依赖）。
2. **服务器侧**：放置 `GameState` 与 `applyAction` 到 `Room`，所有 `ACTION.*` 经 `processAction` 校验后调用 `applyAction`。
3. **客户端侧**：UI 改为"订阅服务器事件驱动"——收到 `room_state`/`event` 即重绘；玩家点击只调用 `client.sendAction(...)`。
4. **最小可玩切片先行**：先打通 `roll → 移动 → end_turn → 聊天 → 重连` 五条链路（本仓库参考实现已含），再逐步补"买地/建房/交易/抽牌/胜负"。
5. **本地验证**：`npm start` 起服务，开两个浏览器标签（或 `npm test` 跑双客户端冒烟）验证同步与重连。
