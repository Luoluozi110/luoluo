移动端 UI 文字可读性审查报告

本报告基于 feihuaqi-playable 当前 CSS、HTML 与关键 UI 结构进行静态审查，聚焦文字遮挡、对比度、字号、排版拥挤、动态内容溢出，以及不同屏幕尺寸、短视口、横屏和文字放大下的可用性。结论用于指导下一轮 UI 改造；本轮未直接改变线上游戏样式。

审查时间：2026-08-16范围：HUD、弹窗、流派选择、论战、图鉴、结算基准：WCAG 2.2 AA + 真机可读性
4 项 P0浏览器缩放、刘海/底部安全区、固定 HUD 重叠、短视口与键盘遮挡。
多处小字当前 UI 存在 10px、11px、11.5px、12px 的信息文字；窄屏下仍继续缩小。
2 个断点主要依赖 ≤600px 与 ≤380px，尚未覆盖 320px、短高、横屏、文字放大与安全区。

一、结论与优化优先级

核心判断：当前版本已经为 ≤600px 增加 HUD、战斗台和结算页重排，方向正确；但布局仍以固定像素定位和压缩字体为主。它在常见 375–430px 竖屏可能“看起来可用”，却会在 320px、低高度横屏、刘海安全区、软键盘弹出、动态长文案及 150%–200% 文字放大时重新发生遮挡、拥挤或不可读。
P0

恢复文本缩放能力，禁止把“不可缩放”当作布局稳定手段

index.html:5 的 viewport 含 maximum-scale=1, user-scalable=no。这会阻止用户放大文字，也掩盖窄屏真实问题。应允许浏览器缩放，并改用局部棋盘手势处理、弹窗滚动和重排保证布局稳定。

P0

为所有边缘浮层建立安全区与动态视口规则

#attrPanel、#inspBar、#turnInfo、#soundToggle、#menuBtn 都使用固定 top/bottom 值，当前没有 env(safe-area-inset-*) 或 dvh 规则。带刘海、灵动岛、圆角屏和手势条设备容易遮挡文字。

P0

先修正“含义文字”的对比度，再优化装饰色

弱提示色、金色数值、绿色状态与稀有度徽标在宣纸底或渐变底上存在低于 4.5:1 的组合；半透明背景还会使真实对比进一步下降。优先保证规则、状态、奖励、倒计时和可点击控件的文字可读。

P0

让可变长内容进入可滚动/可换行容器

起名输入、题干、天象/文心描述、NPC 机制提示、流派卡叙事和结算说明都可能随着数据变长。必须以可换行、可滚动、可取得完整文本为优先，不可用截断掩盖必需信息。

P1

建立统一文字层级令牌，消除逐组件“缩一号”的堆叠

将正文、辅助、微型标注、按钮、标题统一为 rem 基线、最小字号和行高规范；不要在 600px 断点继续把正文/功能文字缩至 10–11px。

P1

用布局断点与容器查询取代仅按手机宽度压缩

重点覆盖 320px 宽、≤430px 单列卡片、≤480px 动态文字行、≤500px 高短视口和横屏；组件应根据自身可用宽度决定换行，而不只看设备宽度。

P2

将可读性加入回归测试与发布验收

建立截图基线、碰撞检测、文本溢出检测、对比度令牌测试与长文案测试，以防新 NPC、天象、奇遇和玩家名号再次挤坏移动端。

二、移动端常见文字显示问题类型与排查重点

1. 对比度不足

浅色字叠在渐变、毛玻璃、图片或半透明宣纸上；同一文字色在不同底图下对比不稳定。对策是先计算最终合成色，关键信息使用不透明或近不透明承载层，普通文字至少 4.5:1。

2. 字号与容器不匹配

为了塞进固定宽度面板而缩小到 10–11px，或使用大字距导致中文字数占宽激增。对策是让容器重排、换行或滚动，而非继续缩字；功能性正文以 14–16px 为目标。

3. 文字被浮层或安全区遮挡

绝对/固定定位的角标、菜单、悬浮按钮、底部提示与系统刘海、键盘或手势条重叠。对策是统一安全边距令牌，并在弹窗打开时避让或隐藏游戏 HUD。

4. 行高、字距和段距过密

小字号叠加 line-height: 1.2–1.5、较大 letter-spacing，会使长叙事和规则说明拥挤、跳读困难。对策是正文 1.6–1.8、辅助文本至少 1.45，14px 以下避免超过 .08em 的字距。

5. 字色与主题冲突

金、朱、青等主题色能表达语义，但未必适合承载小字号文字。对策是将“状态颜色”与“文字颜色”分离：保留色条/边框表达主题，用深色文字承载内容。

6. 动态文本溢出与截断

玩家 12 字名号、具名 NPC、配置型事件、奖励串和多标签组合，都会突破静态样例。对策是设置 min-inline-size: 0、overflow-wrap: anywhere，仅对非关键字段截断且提供完整内容入口。

7. 软键盘与短视口

居中弹窗在手机输入时可能被键盘顶住；vh 在移动浏览器地址栏伸缩时也可能失真。对策是可滚动 overlay、100dvh、聚焦后自动滚入可视区域。

8. 分辨率与字体渲染差异

布局应以 CSS 像素和可用宽高为中心，而非仅按物理分辨率。仍需在 DPR 1/2/3 和不同系统字体渲染下检查细笔画、浅色小字和楷体标题的真实可读性。

五、推荐的系统性排查流程

01. 文本清单列出所有标题、正文、辅助、数值、状态、倒计时、按钮、输入提示与动态内容。
02. 样式核验检查字号、行高、字距、颜色、背景合成、字体回退和是否允许用户放大。
03. 容器核验检查可用宽高、换行、最小宽度、滚动边界、文本截断和软键盘状态。
04. 层级核验检查 HUD、模态、菜单、提示、刘海区、底部手势条与焦点元素是否相交。
  1. 先测试最坏文本：12 字玩家名号、最长 NPC 名/称号、四行题干、最长奖励串、两枚天象角标、满槽文心、连续机制结算。
  2. 再测试最坏空间：320px 宽、256px 高横屏、375×667、390×844、412×915、768×1024，以及地址栏收起/展开和软键盘打开。
  3. 最后测试最坏偏好：浏览器文字缩放 125%/150%/200%，系统“大字体”，弱网字体回退，降低动态效果，深浅/高亮环境下的屏幕亮度变化。
  4. 为每一状态截屏：开局流派、起名、题卡、奇遇、文心、论战、图鉴、结算、排行榜；把截图基线纳入回归。

八、建议的实施顺序

  1. 第一批：无障碍与遮挡修复。移除 viewport 缩放禁令；补安全区/dvh；修正 overlay 滚动与输入键盘；让 modal 覆盖 HUD 控件；修正高风险色彩。
  2. 第二批：排版系统收敛。建立正文/辅助/微型/标题四级文字令牌；替换散落的 10–12px 必要信息；降低小字大字距；统一长文本换行规则。
  3. 第三批：组件重排。流派卡在 ≤420px 单列；机制结算、升级行、文风行在窄屏纵向；各列表和卡片使用容器可用宽度重排。
  4. 第四批：回归保障。新增移动端截图、溢出、碰撞、长文案与对比度测试；每次新增天象/NPC/奇遇/文心字段时复跑矩阵。
验收目标：移动端不以“把字塞进去”为完成标准，而以“在 320px、短高横屏和 200% 文本缩放下，玩家仍可完整看懂、触达并完成当前任务”为完成标准。棋盘属于可缩放的二维游戏区可以保留独立交互例外，但周围的规则、表单、按钮和文本不应继承这种例外。
参考基线：W3C WCAG 2.2 Understanding SC 1.4.3 Contrast (Minimum)、SC 1.4.4 Resize Text、SC 1.4.10 Reflow。报告结论基于当前代码静态审查；上线前应结合真实 iOS/Android 设备和截图回归完成视觉验证。
